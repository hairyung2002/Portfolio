## 문제 정의

기존 교내 축제 사이트는 시간표, 부스 위치 등 정적인 정보 제공 중심이었다. 사용자는 필요한 정보를 확인한 뒤 바로 이탈했고, 축제 참여를 유도하는 인터랙션 요소가 부족했다.

이에 따라 목표를 "정보 전달 플랫폼"에서 "사용자가 직접 참여하고 축제 경험을 확장할 수 있는 서비스"로 재정의했다. 다만 기능을 늘려가는 과정에서 코드 퀄리티와 인프라 아키텍처까지 고려하려던 초기 의도와 달리, 점차 기능 구현 자체에 집중하게 되었고, "교내 서비스라 공격받을 일 없을 것"이라는 안일한 판단 아래 보안 설정이 전무한 상태로 축일 당일 오전 9시 서비스를 오픈했다. 이 판단은 이후 실제 장애로 이어졌다.

## 담당 영역 및 기여 내용

BE Part Leader로서 아래 역할을 전담했다.
- 백엔드 API 설계 방향 결정 및 개발 일정 관리
- 기능별 구현 분배, 코드 리뷰, 협업 관리
- 배포/인프라 구축 및 운영 환경 관리 (인프라 전 영역 담당)

담당 기능 (풀스택으로 직접 구현):

**1. 이벤트/게임 API 및 페이지**
- 카드 매칭 게임을 통해 주점 부스에서 사용 가능한 쿠폰을 지급하는 이벤트 페이지 풀스택 개발
- 교내 주점 주문 사이트 'D-Order' 팀과 협업하여 외부 API 연동 — 게임 성공 시 발급된 쿠폰을 D-Order 시스템에서 조회하고 사용자에게 전달하는 구조 설계
- 관련 기술: 외부 서비스 연동(D-Order API), REST API 기반 쿠폰 발급 로직

**2. 번역 API 기능**
- Google Gemini API를 연동하여 다국어 번역 기능 제공 (외국인 교환학생 대상)

**3. 사용자 식별 기능**
- 부스 좋아요, 게임 이벤트 중복 참여 방지를 위한 사용자 식별 API 구현
- 방식: 사용자가 최초로 기능(좋아요/게임)을 사용할 때 서버가 세션 ID를 발급하고, 이를 클라이언트의 session storage에 저장하여 식별하는 구조
- **한계 및 회고**: 세션 스토리지 값은 JS로 직접 조작 가능해 중복 참여를 우회할 여지가 있었음. 지금 다시 설계한다면 비로그인 상태에서도 위변조가 어려운 JWT 기반 사용자 판별 방식을 사용할 것

> 기여 범위: 인프라 전 영역 + 위 3개 핵심 기능 풀스택 전담. 인프라 설계부터 외부 서비스 연동, 프론트엔드 구현까지 엔드투엔드로 책임진 영역이 명확히 구분됨.

## 기술적 선택과 이유 (Technical Decisions)

### Decision 1. CloudFront + AWS WAF 기반 방어 구조 도입
- **상황**: 서비스 오픈 당시 EC2 Public IP가 직접 노출되어 있었고 CDN, WAF, Nginx rate limit, DRF Throttle이 전무한 상태였음. 축제 1일차 13:00 `/api/like/`에 초당 100회 이상, 이어서 16:00 `/api/game/success/`에 초당 200회 이상의 비정상 POST 요청이 발생 (공격은 프론트를 거치지 않고 백엔드 API URL을 직접 호출하는 방식)
- **선택지**: (1) EC2 직접 노출 유지 + Django Throttle 적용 vs (2) CloudFront + WAF 기반 앞단 방어 구조
- **1차 대응에서 배운 한계**: 공격 IP(Google Cloud IP) Nginx 차단, DRF AnonRateThrottle(10/min) 적용, 도메인 변경을 순서대로 시도했으나 모두 임시방편에 그쳤음. Throttle은 Django 레벨에서 동작하기 때문에 이미 Gunicorn Worker가 요청을 할당받은 뒤에 검사가 이뤄져 리소스 점유 자체를 막지 못했고, 도메인 변경도 EC2 Public IP로 직접 접근이 가능해 근본 해결이 아니었음
- **결정 및 이유**: 비정상 요청 방어는 애플리케이션 코드 레벨이 아니라 서비스 앞단(네트워크 레벨)에서 처리해야 한다고 판단
- **임계값 설정 근거**: WAF Rate-Based Rule은 "5분간 IP당 100회 초과 요청 시 차단"으로 설정. 이 수치는 임의로 정한 것이 아니라, 공격 발생 이전까지의 GA 활성 사용자 수와 정상 API 요청 빈도를 기준으로 정상 트래픽 범위를 추정해 산출
- **결과**: `Client → CloudFront → AWS WAF → ALB → EC2(Private Subnet) → RDS` 구조로 전환. EC2 Security Group에서 80/443 포트를 CloudFront IP 대역에서만 허용하도록 제한해 Origin 직접 접근을 원천 차단. AWS Managed Rule Set(SQL Injection/XSS 방어)과 IP Reputation Rule도 함께 적용해 다층 방어 구조 구축

### Decision 2. Backend 기반 사용자 식별 구조 (세션 ID 방식)
- **상황**: 게임/좋아요 기능에서 중복 참여를 막아야 했고, 쿠폰 발급은 중복 시 실제 비즈니스 오류(쿠폰 중복 지급)로 이어질 수 있었음
- **선택지**: (1) Frontend에서 참여 여부 관리 vs (2) Backend 기반 사용자 식별/검증
- **결정 및 이유**: 클라이언트 데이터는 신뢰할 수 없고, 쿠폰 발급처럼 실제 가치가 있는 로직은 서버에서 검증해야 한다고 판단해 서버 발급 세션 ID 기반 식별 구조로 구현
- **한계**: 세션 ID를 session storage에 저장하는 방식은 클라이언트 측 값 조작에 취약하다는 한계가 있었음 (위 담당 기능 항목 참고)
- **결과**: 게임 중복 참여 방지, 좋아요 사용자 구분은 가능해졌으나 완전한 위변조 방지에는 한계가 있었던 구조

### Decision 3. 번역 기능 - 외부 LLM API 활용
- **상황**: 교환학생 대상 다국어 번역 기능이 필요했음
- **선택지**: (1) 직접 번역 모델 구축 vs (2) 외부 LLM API 활용
- **결정 및 이유**: 한 달이라는 짧은 프로젝트 기간상 모델 개발보다 빠른 서비스 구현이 중요했고, LLM 기반 번역 품질이 충분히 준수했기 때문에 Gemini API 선택
- **결과**: 별도 ML 인프라 구축 없이 다국어 번역 기능 제공

## 트러블슈팅

### 이슈: L7 HTTP Flood 공격과 SQLite Write Lock으로 인한 서버 장애

**타임라인**

| 시점 | 상황 |
|---|---|
| 1일차 09:00 | 보안 설정 없는 상태로 서비스 오픈 |
| 1일차 13:00 | 1차 공격 — `/api/like/`에 초당 100회 이상 POST 요청 (Google Cloud IP 발) |
| 1일차 13:00~ | 응급 대응: IP 차단(Nginx), DRF Throttling 적용, 도메인 변경 — 모두 임시방편에 그침 |
| 1일차 16:00 | 2차 공격 — `/api/game/success/`에 다수 IP에서 초당 200회 이상 POST 요청, 서비스 응답 불능 상태 돌입 |
| 1일차 16:00~19:00 | 원인 파악 실패, EC2 인스턴스 재생성 및 재배포로 임시 정상화 |
| 1일차 19:00 | 구조적 전환 — CloudFront 도입(EC2 직접 접근 차단), AWS WAF 다층 방어 구조 적용 |
| 2일차 09:00 | K6/Curl 기반 부하 테스트로 방어 구조 검증, 이후 안정 운영 |

**당시 판단했던 원인 (실제로는 부정확했음)**
장애 당시에는 단순히 "공격성 트래픽이 DoS처럼 몰려서 서버가 다운된 것"이라고 판단했음. 서버 다운의 표면적 원인(대량 요청)만 보고 대응했고, 정확한 근본 원인은 파악하지 못한 채 EC2를 재배포해 우선 서비스를 복구했음.

**사후 분석으로 밝혀진 정확한 원인**
프로젝트가 끝난 뒤 DB 로그를 다시 확인하는 과정에서, 실제 장애의 결정적 원인이 SQLite의 Write Lock이었음을 알게 됨.
1. 공격성 대량 POST 요청이 `/api/like/`, `/api/game/success/` 등 DB Write 엔드포인트에 집중
2. SQLite는 파일 기반 Single Write Lock 구조라, 동시 Write 요청이 몰리며 DB 경합 발생
3. 이로 인해 DB를 사용하는 기능들만 `database is locked` 에러로 응답 불능 상태가 됨 — 이것이 실제 서비스 전체 다운의 직접적 원인이었음

**해결 과정**
- 1차 대응(임시방편): 공격 IP 차단, DRF Throttling, 도메인 변경
- 구조 개선: EC2 재배포로 즉시 복구 → CloudFront + WAF 다층 방어 구조로 전환해 근본적으로 악성/과다 요청이 Origin과 DB에 도달하지 못하도록 차단

**결과**
- 악성/중복 요청 대부분을 Edge Layer(CloudFront/WAF)에서 차단해 SQLite에 도달하는 중복 Write 자체를 원천 차단
- 2일차 오전 해외 IP발 재공격 시도가 있었으나 CloudFront 단에서 차단 확인, 이후 2~3일차 서비스 안정 운영

**만약 다시 그 시점으로 돌아간다면**
- SQLite Write Lock이라는 사실을 그 당시엔 몰랐지만, 지금 안다면 우선적으로 **SQLite WAL(Write-Ahead Logging) 모드 전환**을 가장 먼저 시도할 것. RDBMS로의 전면 마이그레이션은 이미 운영 중인 서비스에서 DB 정합성이 꼬이거나 인프라가 중단될 리스크가 있어, 축제 기간처럼 즉시 대응이 필요한 상황에서는 WAL 모드 전환처럼 리스크가 낮은 즉각 조치를 우선하는 것이 더 합리적인 선택이라고 판단

**배운 점**
- 장애의 표면적 증상(서버 다운)과 근본 원인(DB Lock)은 다를 수 있으며, 당시 대응만으로 끝내지 않고 사후에 로그를 재분석해 정확한 원인을 규명하는 과정 자체가 중요한 학습이었음
- DDoS/Flood류 공격은 코드 레벨(Throttle)로 해결되지 않으며, 네트워크/인프라 레벨의 방어 구조가 필수라는 것을 체감
- Public 서비스는 Origin 보호 구조와 WAF가 선택이 아니라 기본값이라는 것을 학습

## 실패/한계 및 이후 개선

**이 프로젝트에서 해결하지 않은 부분**: SQLite는 근본적으로 프로덕션 동시 Write에 부적합한 구조였지만, 이번 프로젝트 기간(한 달) 안에서는 CloudFront/WAF로 중복 요청 자체를 차단하는 방식으로 우회했고, DB 자체를 RDBMS로 마이그레이션하지는 않았다.

**교훈의 이어짐**: 이때 인식한 DB 구조 한계는 이후 2026년 봄 축제 프로젝트에서 MySQL 볼륨 마운트 구조로 전환 적용하며 실제로 개선했다. 하나의 프로젝트에서 얻은 인프라 교훈이 다음 프로젝트의 설계 결정으로 이어진 사례.

**리더십 측면에서의 한계와 배운 점**
BE 파트 리더로서 팀원의 부담을 줄이겠다는 생각으로 인프라 설계, 배포, 핵심 기능 구현, 보일러플레이트 구현, 장애 발생 시 에러 핸들링까지 대부분을 직접 담당했다. 그러나 이는 결국 프로젝트 전체가 리더 개인에게 과도하게 의존하는 구조를 만들었고, 본인이 불가피하게 개발에 참여하지 못하는 시간에는 병목이 발생했다. 이 경험을 통해 리더의 역할은 "내가 대신 다 해내는 것"이 아니라 "팀원이 각자의 역할을 해낼 수 있도록 지원하고 병목을 없애는 것"임을 배웠다.

**장애 대응 체계의 한계**
장애를 인지한 계기가 팀원의 수동 발견이었고, 별도의 모니터링/알림 체계가 없었다. 로깅과 웹훅을 연동해 장애나 이상 트래픽 발생 시 Discord 등으로 자동 알림이 오는 구조였다면 장애 인지 시점을 앞당기고 초기 대응 속도를 높일 수 있었을 것이라는 아쉬움이 남는다.

**기타 아쉬운 점**
- 초기 운영 환경 검증(부하 테스트, 보안 점검) 부족 — 실제 운영 중 장애를 겪고 나서야 구조 개선
- "교내 서비스니까 공격받지 않을 것"이라는 안일한 가정으로 보안 설정 없이 서비스를 오픈한 초기 의사결정 자체가 근본 원인 중 하나

## 자소서/면접에서 쓸만한 포인트 메모

- **Backend/Full Stack 지원 시**: 실제 공격 발생 → 임시 대응의 한계 파악 → 근본 원인(SQLite Lock) 규명 → 다층 방어 구조 설계까지 이어지는 트러블슈팅 전 과정. 특히 "장애 당시엔 몰랐던 원인을 사후 로그 분석으로 규명했다"는 지점은 문제 해결 태도를 보여주는 강력한 사례
- **Software Engineer 지원 시**: SQLite Lock 구조에 대한 이해, WAL 모드 vs RDBMS 마이그레이션의 Trade-off 판단(운영 중 리스크를 고려한 점진적 접근), 세션 기반 식별의 한계와 JWT 대안 비교
- **Problem Solver 지원 시**: 표면적 증상과 근본 원인을 구분해서 진단한 과정, "그때는 몰랐지만 지금 안다면 무엇을 먼저 할 것인가"에 답할 수 있는 사후 회고 능력
- **PM/Product Engineer 지원 시**: D-Order 팀과의 외부 협업 조율 경험, 8인 BE 팀 리딩 경험과 그 과정에서 얻은 "리더는 대신 해주는 사람이 아니라 지원하는 사람"이라는 리더십 교훈
- **성장/이어짐 스토리**: 이 프로젝트의 한계(DB 구조, 모니터링 부재)를 인지하고 다음 프로젝트에서 실제로 개선까지 이어간 경험 — 교훈을 다음 실행으로 연결하는 태도
