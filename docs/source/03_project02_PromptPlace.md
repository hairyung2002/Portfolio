## 문제 정의

생성형 AI 서비스 확산으로 프롬프트의 중요성이 커졌지만, 양질의 프롬프트를 체계적으로 거래·공유할 수 있는 플랫폼은 부족했다. 프롬프트 제작자는 자신의 노하우를 수익화할 창구가 없었고, 사용자는 검증된 프롬프트를 찾기 위해 커뮤니티나 SNS를 일일이 탐색해야 했다. 기존 프롬프트 공유 서비스 대부분이 단순 게시판 형태에 머물러 검색·구매·판매·정산까지 이어지는 하나의 생태계를 제공하지 못한다는 점에서, 프롬프트를 하나의 디지털 상품으로 다루는 마켓플레이스를 목표로 설정했다.

## 담당 영역 및 기여 내용

Frontend Engineer로서 아래 기능을 전담했다.

**1. 프롬프트 둘러보기 (메인 페이지)**
- 프롬프트 목록/카테고리별 탐색, 카드 UI, API 연동

**2. 프롬프터 둘러보기**
- 판매자 목록/프로필/판매 프롬프트 조회
- (트러블슈팅 발생 지점 — 아래 트러블슈팅 섹션 참고)

**3. 결제 시스템**
- 목적: 프롬프트를 단순 공유 게시물이 아니라 디지털 상품으로 거래하기 위해 결제 시스템 구축
- PortOne SDK 연동, 결제 요청/완료/실패 처리, 주문 생성
- (트러블슈팅 발생 지점 — 아래 트러블슈팅 섹션 참고)

**4. 판매자 정산**
- 목적: 판매자가 프롬프트 판매 수익을 실제로 관리하고 받을 수 있도록 정산 기능 구축
- 정산 신청, 정산 내역 조회, 정산 계좌 등록/수정

**5. 관리자 대시보드**
- 목적: 운영자가 판매자와 정산 현황을 관리할 수 있도록 관리자 기능 구현
- 판매자 관리, 정산 승인, 서비스 운영 기능

**+ Backend API 연동 및 FE 코드 리팩토링** 전반 담당

> 기여 범위: FE 3인 팀 내에서 결제·정산·관리자 기능이라는 서비스의 핵심 비즈니스 로직 전반을 전담. 임의의 기여도 %보다, 실제 서비스 운영에 필요한 핵심 기능 5가지를 엔드투엔드로 구현했다는 점으로 설명하는 것이 더 정확함.

## 기술적 선택과 이유 (Technical Decisions)

### Decision 1. PortOne SDK를 활용한 결제 시스템 구축
- **상황**: 실제 결제가 이루어지는 서비스라 신뢰성 있는 PG 연동이 필요했음
- **선택지**: (1) PG사 직접 연동 vs (2) PortOne SDK 활용
- **결정 및 이유**: 프로젝트 규모/일정상 빠른 구현과 안정성이 중요했고, 복수 PG를 하나의 인터페이스로 다룰 수 있다는 점이 유리하다고 판단해 PortOne SDK 채택
- **결과**: 실제 운영 가능한 결제 기능 구현 (세부 트러블슈팅은 아래 참고)

### Decision 2. 관리자 페이지 분리
- **상황**: 판매자 관리, 정산 승인 등 관리자 기능은 일반 사용자 기능과 목적·권한이 달랐음
- **결정 및 이유**: 일반 사용자 UX와 관리자 기능은 목적이 다르므로, 권한 관리와 유지보수성을 위해 별도 페이지로 분리
- **결과**: 관리자 전용 페이지로 운영 기능(판매자 관리/정산 승인)을 분리해 유지보수성 확보

### Decision 3. TanStack Query + Axios 레이어 분리 구조 적용
- **배경**: 이 컨벤션(apis/ 레이어에서 axios로 실제 요청 → hooks/queries, hooks/mutations 레이어에서 TanStack Query로 감싸는 3단 구조)은 본인이 설계한 것이 아니라, 팀의 시작점이었던 UMC 동아리 워크북에서 제시된 컨벤션을 따른 것
- **본인의 역할**: 설계자는 아니었지만, 이 구조가 왜 필요한지(캐싱, 전역 데이터 동기화, API 호출과 상태 관리의 관심사 분리)를 이해하고 본인이 담당한 결제·정산·관리자 기능에도 일관되게 이 패턴을 적용
- **실제 규모**: apis/ 폴더 약 30개 파일, hooks/queries·hooks/mutations 100개 이상 훅에 팀 표준 컨벤션으로 정착
- **결과**: 결제/정산/관리자처럼 데이터 정합성이 중요한 기능에서도 안정적인 캐싱과 상태 동기화 확보
- **이후 확장**: 이 프로젝트에서 이해한 TanStack Query 캐싱/관심사 분리 구조를, 이후 본인이 프론트엔드를 담당하는 모든 프로젝트에 공통 컨벤션으로 직접 적용하고 있음 — 따라온 구조를 본인의 표준으로 흡수한 사례

## 트러블슈팅

### 이슈 1. useState Lazy Initializer로 인한 팔로우 상태 동기화 문제 (초기값 + 리렌더링 이슈 + Optimistic Update)

메인 페이지에서 프롬프트/프롬프터를 모아 보여주는 파트에서 발생. 3단계에 걸쳐 시행착오를 거쳐 해결.

**1단계 — 초기값 문제**
- 증상: 로그인 후 메인 페이지 접속 시 팔로우/언팔로우 상태가 제대로 반영되지 않음
- 원인: `useState`의 lazy initializer는 첫 렌더링에서만 평가됨. 팔로잉 목록(`myFollowingData`)은 비동기로 가져오므로 첫 렌더링 시점엔 `undefined`이고, `Boolean(undefined)`가 `false`로 고정되어버림
- `useEffect`로 간단히 고칠 수도 있었지만, 이를 쓰면 공용 mutation 훅을 만든 설계 의도(관심사 분리)가 퇴색된다고 판단해 다른 방법을 모색

**2단계 — 파생값으로 전환, 그러나 리렌더링 문제 발생**
- 시도: `useState` 없이 `myFollowingData`와 `prompter.user_id`로부터 매번 계산되는 파생값(derived state)으로 `isFollow`를 변경
- 결과: 초기값 문제는 해결됐지만, 사용자가 팔로우 버튼을 클릭한 뒤 화면이 리렌더링돼야만 상태가 반영되는 문제가 새로 발생
- 강제 리렌더링은 검색/정렬/필터링 상태 유지 등 UX 측면에서 좋은 방법이 아니라고 판단해 배제

**3단계 — Optimistic Update 도입**
- 해결: `onMutate`/`onError`/`onSettled`를 활용한 Optimistic Update로 캐시를 먼저 갱신해 즉각적인 UI 반응을 구현
- **한계**: 팀원 간 협업 구조상 `onSettled`에서 쿼리를 다시 fetch하는 방식이 이미 정해져 있어, Optimistic Update 본연의 "즉각 반응" 효과가 완전히 살지는 못함
- **이후**: 이 한계는 이후 쿼리키 구조를 재조정하며 개선했으나, 구체적으로 어떻게 개선했는지는 현재 기억이 정확하지 않음 (추가 확인 필요)

### 이슈 2. 결제 순차 호출 — 로컬/운영 환경 차이 (원인 미규명, 그러나 해결함)

- **구조**: 결제 버튼 클릭 → 서버가 주문서 생성 → 클라이언트가 주문서 기반으로 PortOne SDK 결제창 오픈 → SDK 결제 완료 → 그 결과를 서버에 결제 완료 검증 요청. 즉 "서버 검증 요청은 SDK 결제가 실제로 완료된 이후에만 나가야 하는" 순차 구조가 필요했음
- **문제**: SDK 결제창이 완전히 열리기도 전에 결제 완료 검증 요청이 먼저 나가버려, 사용자가 결제창을 보지도 못한 채 결제 실패 처리가 되는 현상 발생
- **특이점**: 로컬 환경(실제 SDK가 뜨고 테스트 결제까지 이루어지는 환경)에서는 매번 정상 동작했고, 운영 환경에서는 매번(간헐적이 아니라 일관되게) 실패함. 왜 로컬과 운영에서 이런 차이가 발생했는지는 끝내 정확히 규명하지 못함
- **해결**: SDK 결제가 실제로 완료되기 전에는 서버 검증 요청이 절대 발생하지 않도록, 콜백 기반 Promise 체이닝 구조로 결제 요청 → SDK 완료 → 서버 검증의 실행 순서를 명시적으로 보장하도록 재작성. 이후 완전히 해결되어 현재까지 안정적으로 운영 중
- **정직한 한계**: 근본 원인(로컬/운영 환경 차이가 왜 발생했는지)은 규명하지 못했지만, 재현되는 증상 패턴을 파악해 구조적으로 순서를 보장하는 방식으로 실제 문제를 해결함

## 실패/한계

- 초기에는 컴포넌트 설계와 상태 관리 구조에 대한 고민이 부족해 이후 리팩토링이 필요한 부분이 발생했음
- 팔로우 상태 동기화 이슈에서 Optimistic Update를 도입했음에도, 협업 구조(onSettled refetch)의 제약으로 이론적 효과를 온전히 살리지 못한 채 절충안으로 마무리됨
- 결제 순차 호출 문제의 근본 원인(로컬/운영 환경 차이)을 규명하지 못한 채 구조 개선으로 우회 해결함 — 결과적으로는 안정화됐으나, "왜"에 대한 답은 여전히 남아있는 상태
- **이후로 이어진 습관**: 이 경험 이후, 로컬 테스트 환경의 통과가 운영 환경의 안정성을 보장하지 않는다는 것을 체감하고, 프론트/백엔드를 가리지 않고 코드의 정확성(correctness)뿐 아니라 실제 운영 환경의 부하/변수(capacity)까지 함께 테스트하는 습관을 갖게 됨. 이 주제는 2026 파이콘 세션 발표 주제("Green CI/Red Production: 테스트 코드가 프로덕트 품질을 보장하지 못하는 이유")로도 이어짐 — 단발성 트러블슈팅이 이후 개발 철학으로 확장된 사례

## 자소서/면접에서 쓸만한 포인트 메모

- **Frontend/Full Stack 지원 시**: `useState` lazy initializer의 동작 원리를 정확히 이해하고, 파생값 전환 → 리렌더링 이슈 발견 → Optimistic Update까지 이어지는 3단계 트러블슈팅 과정. 결제 순차 호출 문제를 콜백 기반 Promise 체이닝으로 해결한 경험
- **Software Engineer 지원 시**: React 상태 관리의 근본 원리(초기값 타이밍, 파생값 vs 로컬 state)에 대한 이해, TanStack Query 캐싱 구조를 실제 비즈니스 로직(정산/관리자)에 일관되게 적용한 경험
- **Problem Solver 지원 시**: 첫 번째, 두 번째 시도가 모두 새로운 문제를 낳았음에도 포기하지 않고 세 번째 해결책(Optimistic Update)까지 도달한 과정. 결제 이슈처럼 근본 원인을 100% 규명하지 못해도 재현 패턴을 근거로 실용적인 해결책을 찾아낸 판단
- **PM/Product Engineer 지원 시**: 관리자 페이지를 별도로 분리한 의사결정, 이미 있는 팀 컨벤션(UMC 워크북 기반)을 맹목적으로 따르지 않고 그 설계 의도(캐싱/동기화)를 이해한 뒤 본인 담당 영역에 일관되게 적용한 태도
- **정직함이 강점이 되는 지점**: 아키텍처를 직접 설계하지 않은 부분(TanStack Query 컨벤션)과 원인을 다 밝히지 못한 트러블슈팅(결제 이슈)을 있는 그대로 인정하면서도, 실제로 문제를 해결해낸 경험 — 과장 없는 엔지니어링 태도를 보여줄 수 있음
