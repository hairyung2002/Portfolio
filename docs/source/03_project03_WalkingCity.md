# 프로젝트명: Walking City (AI 산책 코스 추천 서비스)

## 기본 정보
- 한 줄 소개: AWS Bedrock Knowledge Base 기반 RAG를 활용해 사용자 취향에 맞는 동대문구 산책 경로를 추천하는 AI 서비스
- 유형: 해커톤 프로젝트 (K-HTML 해커톤)
- 성과: 200명 참가, 본선 16개 팀 경쟁 중 우수상 수상 (정확한 순위는 2등 또는 3등, 세부 확인 필요)
- 본인 역할: 프론트엔드 개발 직접 담당 + 백엔드/인프라/AI 아키텍처는 팀원과 함께 설계 방향 결정, 기술 자문 및 작업 분배 (직접 구현은 아님 — Wilson과 달리 이 프로젝트에서는 실제 코드 작성 없이 자문/조율 역할이었음)
- 대표 키워드: RAG, Knowledge Base, Spring Boot, AI 활용
- 정량 지표: 없음 (런칭 서비스가 아닌 해커톤 프로젝트 특성상 별도 지표 미측정)

## Tech Stack
- Backend: Spring Boot
- AI: AWS Bedrock, Bedrock Knowledge Base, RAG
- Storage: Amazon S3
- Data: 동대문구 공공 API
- Map: TMAP API

---

## 문제 정의

기존 지도 서비스는 최단 경로, 인기 장소, 단순 키워드 검색 중심으로 동작해 사용자의 취향을 충분히 반영하지 못했다. 반면 LLM만 단독으로 사용할 경우 실제 지역 정보를 충분히 알지 못해 존재하지 않는 장소를 추천하거나 오래된 정보를 활용하는 Hallucination 문제가 발생할 수 있었다. 따라서 **LLM이 실제 지역 데이터를 기반으로 추천하도록 만드는 것**을 핵심 문제로 정의했다.

## 담당 기능

**1. RAG 기반 추천 시스템 (설계 참여)**
- AWS Bedrock 활용, Knowledge Base 구축 방향 설계, 사용자 입력 기반 프롬프트 설계 방향 자문

**2. Knowledge Base 구축 (설계 참여)**
- 동대문구 공공 API(관광지/공원/카페)를 수집 → CSV 정제 → S3 업로드 → Bedrock Knowledge Base 구축 → RAG 검색 데이터로 활용하는 파이프라인 설계에 참여

**3. 산책 경로 추천 로직 (설계 참여)**
- 사용자 입력 → Knowledge Base 검색 → 관련 장소 추출 → LLM 추천 생성 → TMAP API 연동으로 실제 도보 경로 제공하는 흐름 설계

**4. 지도 기능 (프론트엔드 직접 구현)**
- TMAP API 연동, 추천 장소를 실제 도보 경로로 연결하는 프론트엔드 구현 직접 담당

## 기술적 선택과 이유 (Technical Decisions)

### Decision 1. RAG 아키텍처 채택 이유
- **상황**: LLM 단독으로는 동대문구의 실제 관광지·공원·카페 정보를 충분히 반영하지 못함
- **결정 및 이유**: 공공 API 데이터를 CSV로 정제해 S3와 Bedrock Knowledge Base를 구축하고, 질문 시 관련 데이터를 검색한 뒤 LLM에 함께 제공하는 RAG 구조 적용
- **결과**: 지역 특화 추천이 가능해지고 Hallucination 감소, 실제 데이터 기반 추천 구현

### Decision 2. 전국이 아닌 동대문구로 스코프 제한
- **상황**: 전국 단위 데이터를 구축할지, 특정 지역에 집중할지 선택이 필요했음
- **결정 및 이유**: 전국 데이터를 얕게 다루는 것보다 특정 지역을 깊게 다루는 것이 추천 품질을 높인다고 판단. 동대문구 공공데이터가 가장 안정적으로 제공되어 지역 특화 방향을 선택
- **결과**: 범용 추천 서비스 대비 동대문구 내에서는 높은 추천 정확도 확보

### Decision 3. TMAP API 연계
- **상황**: 장소만 추천해서는 사용자가 실제로 이동하기 어려움
- **결정 및 이유**: 추천 장소들을 TMAP API로 연결해 실제 걸을 수 있는 산책 코스로 제공
- **결과**: 추천과 실제 이동이 하나의 사용자 경험으로 이어지는 서비스 구현

## 실패/한계

**핵심 한계 — 비동기 처리 미흡으로 인한 동시 요청 처리 불가**
AWS Bedrock이 해외 리전 서버라 기본적인 네트워크 레이턴시가 있었던 것도 사실이지만, 더 근본적인 문제는 **비동기 처리가 미흡해 서버가 한 번에 하나의 AI 요청만 처리할 수 있었다**는 점이었다. 여러 사용자가 동시에 추천을 요청하면 순차적으로만 처리되어 응답 지연이 누적되는 구조적 한계가 있었다.

> 이 한계는 이후 Wilson 프로젝트에서 실제로 극복함 (Wilson 프로젝트 파일 참고) — 동시 다발적인 AI 요청 처리라는 동일한 문제를, 이번에는 직접 백엔드 아키텍처를 설계/구현하며 해결한 경험으로 이어짐

**역할상의 한계**: 인프라/AI 아키텍처 설계와 기술 자문은 했지만, 실제 코드 구현에는 참여하지 않아 이 영역에 대한 직접적인 구현 경험치는 없음

## 성과

- K-HTML 해커톤 본선 진출 (200명 참가, 본선 16개 팀 경쟁) 및 우수상 수상 (정확한 순위는 2등 또는 3등, 세부 확인 필요)
- AWS Bedrock Knowledge Base 기반 RAG 아키텍처를 설계/기획해본 경험
- 공공데이터를 활용한 AI 서비스 기획 경험
- 지도 API와 AI 추천 시스템을 연계하는 서비스 흐름 설계 경험

## 자소서/면접에서 쓸만한 포인트 메모

- **Problem Solver 지원 시**: LLM 단독 사용의 Hallucination 문제를 인식하고, RAG로 실제 데이터 기반 추천으로 전환한 문제 정의 → 해결 흐름. "왜 전국이 아닌 동대문구인가"처럼 스코프를 의도적으로 좁혀 품질을 높인 판단
- **PM/Product Engineer 지원 시**: 직접 구현보다 아키텍처 설계와 팀 기술 자문/작업 분배를 담당한 경험 — Wilson과 함께 "설계와 조율"이라는 일관된 포지션을 반복해서 맡아온 패턴으로 엮을 수 있음
- **성장 서사 (Wilson과 연결)**: 이 프로젝트에서 겪은 "비동기 처리 미흡으로 인한 동시 AI 요청 처리 불가"라는 한계를, Wilson에서 본인이 직접 백엔드/인프라를 구현하며 실제로 해결한 경험으로 이어서 서술 가능. 같은 문제를 다른 위치(자문 vs 구현)에서 두 번 마주하고 결국 해결까지 이끈 스토리
- **Software Engineer 지원 시**: 상대적으로 약한 소재 — 코드 레벨보다 아키텍처/기획 레벨의 판단이 중심이므로, 이 트랙에서는 비중 있게 쓰기보다 보조 소재로 활용 권장
